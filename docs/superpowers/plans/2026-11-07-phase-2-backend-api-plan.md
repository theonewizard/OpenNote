# Phase 2 Backend API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The v1 HTTP API on top of the Phase 1 vault engine: authentication (OAuth 2.0 code + PKCE, local login, OIDC upstream, refresh rotation, devices, personal access tokens, web cookie + CSRF), vault, note, folder, attachment, tag and search endpoints with preconditions and idempotency, an audit log and rate limits, and contract tests against the committed OpenAPI document (milestone M2: contract tests green).

**Architecture:** Routers under `backend/app/api/` (one module per area) call the existing library code; every write goes through `app.sync.commit.Committer`, run in a thread pool because it does blocking `fsync` I/O. A new `app.auth` package holds the credential store (users, devices, refresh tokens, sessions, personal access tokens, signing keys) and the three credential checks. Vault access is resolved once per request into a role (`viewer`, `editor`, `owner`); a vault the caller cannot reach is a 404.

**Tech Stack:** FastAPI, Pydantic, SQLAlchemy 2 (async for reads, the sync `Session` inside the Committer), PostgreSQL 18 (`tsvector` + `pg_trgm` for search), Valkey (rate-limit counters), new runtime dependencies `python-multipart` (form and multipart bodies, which FastAPI needs), `pyjwt[crypto]` (EdDSA access tokens, OIDC ID-token checks with `PyJWKClient`), `argon2-cffi` (Argon2id), `filetype` (attachment type sniffing); dev `schemathesis`.

**Spec:** `docs/superpowers/specs/2026-10-17-opennote-architecture-design.md` §7.2 and §10, `docs/api/api-contract.md` ("API §n"), `docs/architecture/sync-protocol.md` ("sync §n"), ADR-0012 (authentication), ADR-0013 (API style), roadmap items P2-01 to P2-10. Repository rules: `CLAUDE.md` (§12 deny by default, §13 RFC 9457).

## How this phase is run

Flemming asked on 2026-11-07 for the phases to be developed in parallel. Phase 2 is therefore split so that other threads can start before it is finished:

1. **Contract first (Task 1, its own pull request).** Every v1 route of P2-02 to P2-09 exists with its final path, parameters and schemas, behind the real auth dependency, answering `501 not-implemented`. `docs/api/openapi.json`, `web/src/api/schema.d.ts` and the Swift package's copy are regenerated, so the web (Phase 3) and Apple (Phase 4) threads build against the real contract. Implementation tasks fill the routes in without changing their shape; a shape change after Task 1 is announced to those threads.
2. **Foundation (Tasks 2 and 3, sequential).** The per-vault lock fix, then the credential store, the principal, vault access and the shared HTTP conventions that every stream uses.
3. **Five parallel streams (Tasks 4 to 8)**, each in its own worktree and branch off the foundation, each with its own test database (`opennote_<stream>_test`) and Valkey database, merged back into `feature/phase-2-api` as they finish.
4. **Close-out (Task 9):** Schemathesis, docs, status.

Collision rules with other threads (proposed by the planning thread on 2026-11-07): one Alembic migration per stream with a fixed number (below), rebased onto `main`'s head before merge, merged migrations never renumbered; this phase's rulings are numbered `R-P2-nnn`.

## Decisions taken in this plan (rulings, no owner decision needed)

- R-P2-001: contract first, stub routes answer 501 behind the real auth dependency (planning thread's proposal; nothing reaches a stub without credentials, and today no credentials exist).
- R-P2-002: one combined dependency `get_caller` accepts a bearer access token, the web session cookie or an `X-API-Key` personal access token, and is added to the guard's auth dependencies. Routes that only a person may call (user admin, tokens, devices, vault administration) use `get_current_principal` (bearer or cookie), so a personal access token cannot mint more tokens.
- R-P2-003: access-token signing keys (Ed25519) are generated by the server on first use and kept in PostgreSQL (`signing_keys`), with a `kid` in every token and the previous key accepted until its tokens expire. No new required setting, rotation by inserting a key. A database leak already exposes every note, so a key there adds no new class of exposure.
- R-P2-004: the web client uses a server-side session (opaque cookie `opennote_session`, httpOnly, Secure, SameSite=Strict, hashed in `sessions`) instead of tokens; CSRF is double-submit: cookie `opennote_csrf` (readable by JavaScript) must equal header `X-CSRF-Token` on `POST`, `PUT`, `PATCH`, `DELETE`, and is an HMAC of the session id so it cannot be planted.
- R-P2-005: OAuth clients are public clients known to the server: `opennote-apple` (redirect `opennote://auth/callback`) and loopback redirects `http://127.0.0.1:<port>/callback` for command-line tools (RFC 8252 §7.3). There is no dynamic client registration.
- R-P2-006: OIDC upstream providers come from `OPENNOTE_OIDC_PROVIDERS` (JSON list: `name`, `issuer`, `client_id`, and the client secret from `OPENNOTE_OIDC_<NAME>_CLIENT_SECRET_FILE`); discovery, token exchange and JWKS use the standard library and `PyJWKClient`, no HTTP client dependency. `GET /api/v1/auth/authorize?provider=<name>` starts the upstream login, so the keyless list gains no extra route. Users are matched on (`issuer`, `sub`), never on e-mail.
- R-P2-007: the first administrator is created on the server with `python -m app.auth.admin create-user --admin <username>` (password on standard input); there is no keyless bootstrap route.
- R-P2-008: `POST /api/v1/devices` from the API contract is dropped: a device is created by its first token exchange (`device_name`, `device_platform` on `/auth/token`). Added to the contract: `/api/v1/users` (admin), `/api/v1/vaults/{id}/members`, `GET /api/v1/attachments`, `POST /api/v1/auth/logout`.
- R-P2-009: the per-vault lock (Task 2) is a PostgreSQL session advisory lock on the vault id, taken by the outermost `Committer.commit` and `recover` call and held until the vault file is written; a thread-local depth counter lets the nested commits (`_absorb`, `_settle`) run under the lock they are already in. It serializes the API workers and the watcher process alike, which a process-local lock would not.

## Global Constraints

- Deny by default: every route has `get_caller`, `get_current_principal` or `get_api_key`, or is in `KEYLESS_ROUTES` (API §2); `test_route_auth.py` pins the keyless set.
- Unauthorized vault, note or attachment: `404` with the same body as a missing one (API §1 Authorization).
- `PUT`, `PATCH`, `DELETE` on revisioned resources: missing `If-Match` is `428 precondition-required`, stale is `412 precondition-failed` with the current resource under `current`. Responses carry `ETag: "<revision>"`.
- `POST` with `Idempotency-Key`: the first response (status, body, `ETag`, `Location`) is stored for 24 h per principal and key and replayed; the same key with a different body is `422 idempotency-key-reused`.
- Note bytes in and out unchanged; `content_hash` is computed from the exact bytes; no endpoint reformats a note (storage §2.1).
- Every write goes through `Committer.commit` with `device_id` = the caller's device id, `web` for a session, or `pat:<token id>`.
- Secrets: passwords as Argon2id; refresh tokens, session ids and personal access tokens stored as SHA-256 only; no secret is logged or returned twice.
- Tests use real PostgreSQL, Valkey and temporary vault directories; nothing under test is mocked (testing §1).
- `make lint typecheck test` and `make openapi` (drift clean) before every merge; `ponytail-audit` before the implementation pull request is marked ready.

## Review Focus

- Refresh-token reuse: presenting a spent refresh token revokes the whole device (`test_refresh_reuse_revokes_device`).
- CSRF: a cookie-authenticated `POST` without or with a wrong `X-CSRF-Token` is `403`; a bearer request needs none (`test_csrf_matrix`).
- A personal access token scoped to vault A gets 404 on vault B and 403 on a write with `scope=read` (`test_pat_scope_matrix`).
- Two concurrent `PUT`s of one note with the same `If-Match`: exactly one wins, the other gets 412, and the vault file holds the winner's bytes (`test_concurrent_puts_one_wins`, with the Task 2 lock).
- An attachment uploaded as `image/png` that is really HTML is stored as `text/html` and served as a download with `nosniff` (`test_html_disguised_as_png_is_downloaded`).
- Search never returns a hit from a vault the caller cannot reach, even when `vault_id` is omitted (`test_search_is_scoped`).

## Errata

(Departures from this plan are listed here as they happen.)
- Task 2: besides the advisory lock, a process-local lock per vault is taken first, so threads of one process queue on it instead of each holding a pooled database connection while blocked in `pg_advisory_lock` (which could starve the pool and stall the lock holder).
- Task 3: `0006_auth` also holds the vault metadata columns and `audit_events` (append-only by trigger) with the `app.core.audit.audit()` helper, so the streams that call it (auth, notes) do not wait for Task 8; search's migration becomes `0007_search`. The AI thread's pull request #37 also adds a `0006`: whichever merges second renumbers its migration onto the other's head.
- Task 4: an unsupported `grant_type` is a 422 validation problem (the published signature lists the two grants); every other token error is a problem with an extra `error` member carrying the RFC 6749 code, and `Cache-Control: no-store`. A presented code is spent even when the verifier, client or redirect is wrong. Logout with a bearer marks the device's refresh tokens used, so presenting one later counts as reuse. Client `opennote-web` (redirect `/`) exists only for `authorize?provider=` (web OIDC login). `POST /tokens` does not replay an `Idempotency-Key` (the secret is shown once); `POST /users` leaves the password out of the idempotency fingerprint.
- Task 5: `app.api.deps.commit` takes `expected_revision` and re-checks it inside the vault lock (`StaleRevision`): without it, a racing `PUT` based on the previous revision was merged or became a conflict copy instead of a 412 (`test_concurrent_puts_one_wins` failed). Note content is read from the history store, so it always matches the `ETag`. A folder move refuses (422) when any file in it breaks the path rules; a failure part-way keeps the moves already made.
- Task 6: uploads are authenticated before the body is read and cut off past `max_blob_bytes` + 64 KiB; the media type is sniffed on read (first 8 KiB, cached by content hash), not stored. Downloads stream from the vault file and fall back to the history store when the size differs. The api's `/tmp` (upload buffer) is raised to 1Gi in Helm and kustomize.
- Task 7: search uses migration `0007_search` (`search_documents`, filled by `index_file` and `rebuild_index`; the migration cannot backfill, a rebuild does). `before:`/`after:` are strict on the modified day; `title:` is a substring match. Search hits share the note endpoints' metadata assembly.
- Task 8: rate limits count before routing (failed logins count); 0 disables a limit, and the test fixtures disable them by default. Valkey down: requests pass (fail open, logged once a minute). Behind the web proxy every client is one IP until `FORWARDED_ALLOW_IPS` is set; put to Flemming.
- Task 9: Schemathesis runs in-suite against uvicorn on a local port with a bearer token, 100 examples per operation; `positive_data_acceptance` is excluded (schema-valid requests are rightly refused by business rules: unknown OAuth client, invisible vault, path rules, stale `If-Match`). It found three defects, fixed: 405 `Allow` named only the first route of a path; request booleans accepted `"0"`; NUL in a body string was a 500.
