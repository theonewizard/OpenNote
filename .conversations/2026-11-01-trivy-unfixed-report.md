## Rulings

- R117: `.trivyignore.yaml` is read by the report steps only, never by the gates. On a gate the file could only ever suppress a `fixed` finding, that is weaken it, and the suppressed finding would then also be missing from the report, which filters `fixed` out (the research panel's first objection to R114). Cost if wrong: a reviewer who wants the ledger on the gate adds `--ignorefile` to two lines.
- R118: the report steps carry `continue-on-error: true`, and a failed Trivy call is written into the summary (`trivy exited N`) and recorded in a `status` variable the step exits with, as the gate step does. Both workflows run steps with `bash -eo pipefail`, so without `continue-on-error` a Trivy CLI error (a flag change after a bump, a YAML error in the ledger, a database download failure) would turn a green gate red from a report-only step (the panel's second objection); the draft used `|| echo` alone, which kept the step green on every Trivy failure, so a broken report would have gone unnoticed until someone read the summary text (the review's finding). `--exit-code 0` covers findings; `continue-on-error` keeps the job green; the step's own red mark and the runner's exit-code annotation say that the report, not the gate, broke. Trivy's log lines stay on stderr, that is in the job log, not in the summary.
- R119: the docker group in `dependabot.yml` becomes `docker-base-images` with `patterns: ["*"]` and `group-by: dependency-name` and no `update-types`: GitHub documents `group-by` as the way to one pull request per dependency across the listed directories, and does not document how a digest-only bump is classified, so the minor-and-patch filter goes. `patterns: ["*"]` is kept so the group states what it covers; GitHub's documented monorepo example uses `group-by: dependency-name` alone, and the SchemaStore schema for `dependabot.yml` accepts both forms. Cost if wrong: a configuration error shows on the repository's Dependabot page and Dependabot keeps the previous behaviour until it is fixed.
- R120: `IMPLEMENTATION_STATUS.md` and `ROADMAP.md` are updated here after all. While the draft was written, pull request #19 changed the same lines, so the plan was to update them once both were on `main`; #18 and #19 were merged (main `eb97601`) before this branch was pushed, so the branch was restarted on that main and the two status rows now describe the report steps and the Dependabot group as made. The 2026-11-01 decisions record stays as merged; this record is its own file.
- R121: the flags were verified on Trivy 0.76.0 (the release CI pins, downloaded from its GitHub release and checked against the release checksums) in the cloud container: `--ignore-status fixed` is accepted (the flag's values are unknown, not_affected, affected, fixed, under_investigation, will_not_fix, fix_deferred, end_of_life), an empty `vulnerabilities: []` ledger is accepted, an entry with a future `expired_at` moves the finding to the "Suppressed Vulnerabilities" table with its Statement and Source columns and a past date brings it back (checked with the report step's exact flags on a scratch `requirements.txt` with `ecdsa==0.19.0`, CVE-2024-23342, status `affected`; a first check with `requests==2.19.0`, CVE-2018-18074, had run without `--ignore-status fixed`, and with it a fixed finding is dropped before the ignore file is read, so a ledger entry for a fixed finding is a no-op, as the ledger header now says), the gate flags without `--ignorefile` do not pick `.trivyignore.yaml` up from the working directory (the fixed finding was still reported and failed the scratch gate with the file present, so R117 holds), and the `trivy fs` report step ran end to end as written against this repository in 20 s including the database download, writing 27 summary lines and exiting 0. The image steps use the same flags; their first real output is this pull request's containers run.
